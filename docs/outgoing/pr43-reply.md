## a) How many times can it call itself.

**Answer.** It calls itself at most `DUN_DEPTH` times — 10 in The Goblin Caves, 15 if the player selects Challenge difficulty — because every self-call descends exactly one level and the last of them faults on a null resource instead of returning. That maximum needs the outermost entry to arrive on level 1 and land on chasm. Two call sites can do it with nothing else going right, because they arrive with `safe=false` and skip the step-off: the spell Shift Level, which blocks ascent only at depth 1 (`lib/wspells.irh:7057`) and reaches `MoveDepth` through the binding that drops the second argument, and wizard Ascend/Descend, which accepts a depth of 1 (`Debug.cpp:804-810`). The ordinary `MoveDepth` arrivals on level 1 — the up-staircase (`Feature.cpp:260` with `DepthMod = -1`), the two skylight routes, by levitation and by rope (`Skills.cpp:4008`, `:4066`), and resurrection (`Prayer.cpp:1482`) — all pass `safe=true`, so each of those needs the landing square and all eight of its neighbours to be chasm before it can begin a chain. A chain that instead begins by falling from level 1 is one shorter. Counting entries rather than self-calls gives one more again, which is why section (b) totals sixteen `MoveDepth` entries. The bound also assumes no module defines `BELOW_DUNGEON`: with one defined, `Feature.cpp:885-888` subtracts `DUN_DEPTH` and enters the next dungeon at its level 1 instead of faulting, and the bound becomes the sum along that chain.

**Measured.**

Which branch ran hardly matters for the conclusion, and that part is arithmetic on the source rather than anything I ran: the null read at `Feature.cpp:887` sits forty lines above the `safe` test at `:927`, so `safe` is beside the point whoever passes it.

One method note, because it cost me a day. **Map content is not a property of the seed alone.** Generation consumes the RNG stream, so a session that descends straight to depth 10 gets a different level 10 from one that walked the nine above it. A straight descent on seed 3362 produced a depth 10 with zero chasm squares where the survey below recorded 282. The key scripts replay the survey's exact path for that reason.

The bottom level really does have holes with nothing under them. Eight seeded headless sessions, one run directory each, 60 generated levels ([depthprobe-8seeds.log](https://github.com/networkingguru/incursion-roguelike/blob/1ef5f2988240ed16a1019bbec8014e46cbc3d284/docs/evidence/inc-x9i/depthprobe-8seeds.log)): all three sessions that reached depth 10 found chasm there — 16, 282 and 21 squares — and on those levels the generator was asked for no down-stairs at all (`stairs_down=0`). Sixteen of the 31 generated levels shallower than `MIN_CHASM_DEPTH`, which defaults to 5, carry chasm too.

Challenge difficulty really does deepen the dungeon, which I had only read before. `OPT_DIFFICULTY` is byte 117 of `Options.Dat`; the shipped file holds 2. Set it to 3 and the same script reports `dun_depth=15` at run time on every generated level and reaches depths 11 to 14, which it cannot do at baseline because wizard Ascend/Descend refuses any depth above `DUN_DEPTH` ([depthprobe-challenge-seed3362.log](https://github.com/networkingguru/incursion-roguelike/blob/1ef5f2988240ed16a1019bbec8014e46cbc3d284/docs/evidence/inc-x9i/depthprobe-challenge-seed3362.log)).

**The code behind all that, read rather than run — except where marked.**

Only `Player` re-enters `MoveDepth`. `Thing::MoveDepth` is a one-line `Remove(true)` ([Feature.cpp:850-852](https://github.com/rmtew/incursion-roguelike/blob/7469d3eddf1c4347928854a9494eeefb301d358e/src/Feature.cpp#L850-L852)), so a monster that falls is deleted rather than moved, and `Player` is the only override ([Creature.h:1103](https://github.com/rmtew/incursion-roguelike/blob/7469d3eddf1c4347928854a9494eeefb301d358e/inc/Creature.h#L1103)). The path back into it is a cycle of three functions:

```
Player::MoveDepth        calls PlaceAt          Feature.cpp:935
Thing::PlaceAt           calls TerrainEffects   Display.cpp:219
Creature::TerrainEffects calls MoveDepth        Move.cpp:1380
```

The last step is `MoveDepth(m->Depth + 1)` — always exactly one level down, so the chain is monotonic. It omits the second argument, so `safe` takes the default declared on `Thing` ([Map.h:719](https://github.com/rmtew/incursion-roguelike/blob/7469d3eddf1c4347928854a9494eeefb301d358e/inc/Map.h#L719)), which is `false`, and the fall-avoidance block at [Feature.cpp:927](https://github.com/rmtew/incursion-roguelike/blob/7469d3eddf1c4347928854a9494eeefb301d358e/src/Feature.cpp#L927) is guarded by `safe`. So the path that recurses is one of several that run with `safe=false`, and like all of them it does not step the player off a fall square on arrival.

The ceiling is arithmetic on that. `DUN_DEPTH` is data: 10 for The Goblin Caves (`lib/dungeon.irh:17`), and [Annot.cpp:468-470](https://github.com/rmtew/incursion-roguelike/blob/7469d3eddf1c4347928854a9494eeefb301d358e/src/Annot.cpp#L468-L470) returns 15 for `DUN_DEPTH` on any annotated resource once difficulty is `DIFF_CHALLENGE` or above. Reaching the ceiling needs more than chasm on every level: with `safe=false` the arrival point is the player's own `x,y`, re-rolled only when that is out of bounds, solid or a vault (`Feature.cpp:898`, `:921-925`), so the chain continues where the *same coordinates* are chasm on the level below, or where a re-roll happens to land on chasm — and with 282 of them on seed 3362's depth 10, a re-roll is not a remote possibility. Even so, 15 on Challenge and 10 in The Goblin Caves are bounds, not expectations.

The fault itself: a fall from the bottom level asks for `DUN_DEPTH + 1` and takes the branch at [Feature.cpp:884-887](https://github.com/rmtew/incursion-roguelike/blob/7469d3eddf1c4347928854a9494eeefb301d358e/src/Feature.cpp#L884-L887). No dungeon in `lib/` defines `BELOW_DUNGEON`, so the id is 0, `Game::Get` returns NULL for a zero id ([Res.cpp:312](https://github.com/rmtew/incursion-roguelike/blob/7469d3eddf1c4347928854a9494eeefb301d358e/src/Res.cpp#L312)), and the branch reads `RES(mID)->Type` with no test. The up path reads the same kind of constant thirteen lines earlier and does test it ([Feature.cpp:873-875](https://github.com/rmtew/incursion-roguelike/blob/7469d3eddf1c4347928854a9494eeefb301d358e/src/Feature.cpp#L873-L875)): `if (!mID) return;`.

I had assumed this was unreachable, because [MakeLev.cpp:1452](https://github.com/rmtew/incursion-roguelike/blob/7469d3eddf1c4347928854a9494eeefb301d358e/src/MakeLev.cpp#L1452) says it is: *"No chasms on the last dungeon level, because there is nowhere to fall to!"*. That test, and the `MIN_CHASM_DEPTH` test above it ([:1449](https://github.com/rmtew/incursion-roguelike/blob/7469d3eddf1c4347928854a9494eeefb301d358e/src/MakeLev.cpp#L1449), default 5 at [Annot.cpp:539](https://github.com/rmtew/incursion-roguelike/blob/7469d3eddf1c4347928854a9494eeefb301d358e/src/Annot.cpp#L539)), live in the **streamer** picker. Chasm also arrives as an ordinary **room**, and the room picker applies neither rule. Its gates are the region's `RoomTypes`, then `DepthCR` against the region's own `Depth`, then `MIN_VAULT_DEPTH` for vaults, then `RF_CORRIDOR`, then a scan of what has already been used on this level ([MakeLev.cpp:2397-2404](https://github.com/rmtew/incursion-roguelike/blob/7469d3eddf1c4347928854a9494eeefb301d358e/src/MakeLev.cpp#L2397-L2404)) — no last-level test and no `MIN_CHASM_DEPTH`. Three shipped `RF_ROOM` regions place chasm: `"Twisting Chasm"` (`lib/dungeon.irh:3497`, `Depth: 2`), whose `Floor:` is `$"chasm"`; `"Floating Rock;1"` (`lib/dungeon.irh:3660`, `Depth: 3`), whose floor is obsidian but whose grid tiles `'X'` to `$"chasm"`; and `"Jagged Chasm"` (`lib/dungeon.irh:3644`), which sets `* BLOB_WITH $"chasm"` and declares **no `Depth:` at all**, so the picker's depth gate passes for it at every level of every dungeon. None of the three is `RF_NOGEN`, and since no dungeon defines `ROOM_WEIGHTS`, `GetList`'s default ([Annot.cpp:365](https://github.com/rmtew/incursion-roguelike/blob/7469d3eddf1c4347928854a9494eeefb301d358e/src/Annot.cpp#L365)) puts every non-`NOGEN` `RF_ROOM` region into every dungeon's pool. The survey above does not say which picker placed the chasm it counted, but it is what the room-picker reading predicts.

`safe` decides only whether the *cycle* is entered, not whether the fault is reached, and the three direct-`Descend` crashes above are the proof. The null read is thirty-three lines into the function, at `Feature.cpp:887`; the `safe` test is forty lines below that, at `:927`, so a call from the bottom level faults before `safe` is ever looked at. Both of the branches that could have produced those stacks pass `true`: the levitation branch at `Skills.cpp:4161`, and the `>` command's `Format("Climb down the chasm? (Climb %+d vs. DC %d)", ...)` branch at `:4181`, which on a successful Climb check calls `MoveDepth(m->Depth + 1, true)` and dereferences `RES(0)`. The code path needs no recursion, no trap and no script — a character who presses `>` beside a chasm on the bottom level is in it. My runs are not that character: they reach depth 10 by wizard command and a probe puts the player beside the hole, as described above. What the runs establish is that the branch faults; that an ordinary `>` reaches the branch is the source reading below. The wizard command cannot do that, incidentally: `Debug.cpp:804-805` refuses any depth above `DUN_DEPTH`, which is why in the first crash report the null read is in the nested call rather than in the wizard call itself.

What `safe=true` does buy is that the arrival point steps off a fall square, so those sites enter the *cycle* only when the landing square and all eight of its neighbours are fall squares. Six call sites pass `safe=true`, and four of the six cannot reach the `BELOW_DUNGEON` branch at all: `Skills.cpp:4008` and `:4066` ascend, `Prayer.cpp:1482` passes a literal depth of 1, and the stairs handler at `Feature.cpp:260` would need a down-staircase standing on the bottom level, which the generator never places — `MakeLev.cpp:1879` gates the whole placement loop on `Depth < DUN_DEPTH`, and no region in `lib/` puts one in a grid. The other two are the levitation and successful-climb branches, `Skills.cpp:4161` and `:4181`, and the probe above puts both of them on the bottom level with `safe=true`, crashing.

The levitation branch has a second problem, and this one is measured too. Its guard at `:4158` asks `GetDungeonMap` for `m->Depth + 1`, which on the bottom level is `DUN_DEPTH + 1`. `Feature.cpp:988` allocates `min(MAX_DUNGEON_LEVELS, DUN_DEPTH + 1)` handles — 11 for The Goblin Caves — so the last valid index is `DUN_DEPTH`. A probe that reports any request outside that allocation fires on both levitation runs, and stays silent on both climb runs. Read the silence carefully, because it is narrower than it looks: the probe reports out-of-allocation requests, not calls, so what it shows is that the climb branch never makes one. That the climb runs call `GetDungeonMap` at all — once per wizard depth change — is a reading of the code and the key script, not something this probe measured.

```
GetDungeonMap depth=11 allocated=11 last_valid_index=10 reads_index=11
```

Eleven handles, indices 0 to 10, and the function is asked for index 11. The generation loop at `:1004` runs `i <= Depth`, so it reads `DungeonLevels[n][DUN_DEPTH + 1]` past the end at `:1005`, writes it at `:1007` if that read happens to yield zero, and returns it at `:1017` — which is the value the guard tests, so the read is what lets `Skills.cpp:4161` proceed at all. The defect is in `Game::GetDungeonMap` rather than in the guard.

The `Fatal` at `Feature.cpp:983-984` never runs on this path, which is why nothing catches it: the levitation guard fires while the player stands in that dungeon, so it is already registered and `:979` jumps to `Found:` before the test. It would not catch the case anyway, since it bounds `Depth` against `MAX_DUNGEON_LEVELS`, which is 50 (`Defines.h:4324`), rather than against the handles allocated.

One further site passes nothing at all — besides the recursion itself at `Move.cpp:1380` and the script binding at `dispatch.h:680` — and that is wizard-mode Ascend/Descend at `Debug.cpp:810`, which calls `MoveDepth(i)` and so runs with `safe=false`. That call site sits in `Player::WizardOptions`, the frame at the bottom of the crash report above — my harness reached depth 10 by that route, so the outer call in the trace is itself an unsafe one.

Nor is `MoveDepth` the only way in, which is what the walking crash above shows. `Thing::PlaceAt` fires `TerrainEffects()` for any live creature on both its paths (`Display.cpp:109` same map, `:219` across maps), and `Creature::Walk` calls it too (`Move.cpp:1122`). Flying or levitating avoids the fall. Walking does not, though it is not silent: chasm carries `TF_WARN` and its `EV_MON_CONSIDER` returns `ABORT` for anything neither aerial nor `ELEVATED` (`lib/dungeon.irh:680-686`), so the player is asked to confirm first — `XPrint("Confirm enter the <Res>?", ...)` at `Move.cpp:476-479`, with `<Res>` rendering as the terrain's name. Answering yes is enough, and that is the whole of the shortest route to the fault.

The scripted ones are a different matter, and I think a second defect. The script API declares one parameter — `system void T_THING::MoveDepth(int16 NewDepth);` ([Api.h:226](https://github.com/rmtew/incursion-roguelike/blob/7469d3eddf1c4347928854a9494eeefb301d358e/inc/Api.h#L226)) — and the binding calls the C++ method with one argument ([dispatch.h:680](https://github.com/rmtew/incursion-roguelike/blob/7469d3eddf1c4347928854a9494eeefb301d358e/lib/dispatch.h#L680)), so every scripted call runs with `safe=false`. Two shipped scripts write `,true)` at the call and get `false` for it: `lib/religion.irh:2992-2993`, where Khasrach casts the player down as far as depth 10, and `lib/wspells.irh:7065`. The first can therefore drop a player onto the bottom level's chasm with no avoidance step, which would be a non-wizard route into the fault above. Two ordinary traps create chasm where the player stands. `"small trapdoor trap"` and `"large trapdoor trap"` are `EA_TERRAFORM` effects with `xval: TERRA_FLOOR; rval: $"chasm"` (`lib/threats.irh:799` and `:1085`), and they are `EF_MUNDANE`, which is to say non-magical rather than optional — they ship in `lib/threats.irh`, so no add-on module is involved. The generator places them itself: `MakeLev.cpp:2171` and `:2184` pick a random `AI_TRAP` effect for the level's `DepthCR` and drop a `Trap` on the square, so the trap is in place from generation and the chasm appears when it fires. One firing on the bottom level writes real chasm where the player stands, with no magic, no module and no wizard command — and he falls inside the trap's own call, not on his next step: `Effects.cpp:1601` writes the terrain, then the loop at `:1621-1624` throws `EV_ENTER` and calls `TerrainEffects()` for every creature on that square. **None of this paragraph is measured.** I have not run any of these paths.

## b) Provable maximum stack from recursive calls.

**Answer.** 36,656 bytes for the deepest chain the data allows, which nobody has reached. That is the provable maximum of the recursion's own frames, which is what you asked for; it is a floor on the process's peak, because it excludes `SaveGame` and the other ordinary callees, as below. 2,400 of that for each level descended with this patch applied. Master as it stands today, with the `static`, costs 1,872 a level. The patch's price is therefore 528 bytes a level, of which 512 is the array and 16 is what the compiler allocates alongside it.

**Measured: what a level costs.** A probe recorded `MoveDepth`'s own frame address on entry — `__builtin_frame_address(0)`, evaluated inside the function — and the distance from the frame still open above it: **2,416 bytes**, of which that probe accounted for 16 ([stackprobe-seed3362.log](https://github.com/networkingguru/incursion-roguelike/blob/1ef5f2988240ed16a1019bbec8014e46cbc3d284/docs/evidence/inc-x9i/stackprobe-seed3362.log)). That log holds one nested entry, not many — the `nest=1` lines have nothing above them to measure against.

The prologues of a build carrying the patch and no probe give the same total independently. One level costs three frames, not one, because the recursion runs through `PlaceAt` and `TerrainEffects` ([frames-arm64.md](https://github.com/networkingguru/incursion-roguelike/blob/1ef5f2988240ed16a1019bbec8014e46cbc3d284/docs/evidence/inc-upw.15/frames-arm64.md) has the disassembly):

```
Player::MoveDepth          0x60 +  0x230 =  656
Thing::PlaceAt             0x60 +  0x1b0 =  528
Creature::TerrainEffects   0x60 +  0x460 = 1216
                                   total = 2400
```

**Measured: what the patch costs.** An A/B on one keyword, compiling `Player::MoveDepth` both ways at shipping flags and reading the prologue. Each version has exactly one stack allocation:

```
Thing *GoWith[64]         stp x28, x27, [sp, #-0x60]!    96
                          sub sp, sp, #0x230            560   total  656
static Thing *GoWith[64]  sub sp, sp, #0x80             128   total  128
```

So the keyword is worth **528 bytes**, not the 512 the array itself needs; the compiler allocates 16 more alongside it, and it lays the register saves out differently as well. The `static` build carries `__ZZN6Player9MoveDepthEsbE6GoWith` in `.bss`; the other does not. The patched figure, 656, is byte for byte what the full shipping binary shows, which is the check that compiling the one file measures the same thing as building the game.

**Measured: what those 528 bytes actually buy.** I sent this as hardening. It is more than that, and the difference is observable rather than argued. `static` means one array for the whole process while `gwc` stays a local, so an outer call and a nested one share the array and disagree about how much of it is theirs.

I arranged the state in wizard mode: summon three kobolds, make each a follower, then change depth three times by wizard command — down to 7, back up to 6, down to 7 again. The trip up is what strands a follower on depth 7, through the index skip in (c). The last arrival lands on a chasm square that level already has, so it falls and `MoveDepth` re-enters itself. As in (a), a probe chooses the landing square rather than leaving it to luck: it steers the second arrival at that depth onto an existing `TF_FALL` square, and creates no terrain. Same seed, same key script, two builds differing only in the keyword ([gowith-reentrancy](https://github.com/networkingguru/incursion-roguelike/tree/1ef5f2988240ed16a1019bbec8014e46cbc3d284/docs/evidence/inc-upw.15/gowith-reentrancy)). The probe prints the array's address and its live entries twice per call: when collection finishes, and immediately before the placement loop reads them back.

Upstream's declaration — one address throughout, because the array is in `.bss`:

```
(the first four lines, the descent to 7 and the trip back up, omitted)
collected nest=1 depth=6 array=0x1011f99f8 gwc=1 entries=[0x714f80000]
collected nest=2 depth=7 array=0x1011f99f8 gwc=1 entries=[0x714f80e00]
placing   nest=2 depth=8 array=0x1011f99f8 gwc=1 entries=[0x714f80e00]
placing   nest=1 depth=8 array=0x1011f99f8 gwc=1 entries=[0x714f80e00]
```

The outer call collected `0x714f80000`. By the time it reaches its own placement loop the array holds `0x714f80e00`, the creature the nested call collected. It places that one a second time, and the follower it collected is placed nowhere — it appears in no later line of the log.

With the `static` removed — two addresses, both on the stack, each frame placing what it collected:

```
(same four lines omitted)
collected nest=1 depth=6 array=0x16da74a00 gwc=1 entries=[0x1033408a0]
collected nest=2 depth=7 array=0x16da73bc0 gwc=1 entries=[0x1033416a0]
placing   nest=2 depth=8 array=0x16da73bc0 gwc=1 entries=[0x1033416a0]
placing   nest=1 depth=8 array=0x16da74a00 gwc=1 entries=[0x1033408a0]
```

Both sessions end with the player on depth 8. The patched one lists `k kobold` in Things in View; the unpatched one lists no kobold at all. The outer call's `new_m` is the depth 7 map, so its placement loop puts whatever `GoWith[0]` holds onto depth 7: patched, that is its own follower, and the one the nested call left on depth 8 stays with the player; unpatched, it re-places the nested call's follower and drags it back up from 8 to 7, losing its own. The player arrives alone and one follower is on no map at all.

**Read from the source, not run.** The code behind that trace, for completeness: the outer call collects followers and `Remove`s them from the old map ([Feature.cpp:906-911](https://github.com/rmtew/incursion-roguelike/blob/7469d3eddf1c4347928854a9494eeefb301d358e/src/Feature.cpp#L906-L911)), so they are on no map while it works; `PlaceAt` sets the player's `m` to the arrival level before firing `TerrainEffects` (`Display.cpp:131-132`, `:219`), so the nested `MoveDepth` iterates the arrival level; and the outer frame then resumes at `GoWith[i]->PlaceAt(new_m, nx, ny)` with its own `gwc` ([Feature.cpp:937-938](https://github.com/rmtew/incursion-roguelike/blob/7469d3eddf1c4347928854a9494eeefb301d358e/src/Feature.cpp#L937-L938)).

**Arithmetic on those figures, at a depth nobody has reached.** At `DUN_DEPTH` 15 the chain is sixteen entries: fifteen that complete a move and cost the full 2,400 each, and a sixteenth that asks for `DUN_DEPTH + 1` and faults at `:887` before it reaches `PlaceAt`, so it costs only its own `MoveDepth` frame. That is 15 × 2400 + 656 = **36,656** bytes with the patch and 15 × 1872 + 128 = **28,208** without it. The difference, 8,448, is 16 × 528. That counts the recursion's own three frames only: a true peak adds whatever the deepest ordinary callee needs at the innermost level, and `MoveDepth` calls `theGame->SaveGame(*this)` on every entry (`Feature.cpp:858`), which I have not measured. Against the 8 MB main-thread stack on macOS, or the 1 MB Win32 default, 36,656 is about 3.5% of the smaller figure, so stack is not the constraint here. That comparison is unkind to the patch, since every figure above is from an LP64 build: on your Win32 target the pointers are four bytes, so the array itself is 256 rather than 512 and the totals fall accordingly. At the arm64 figure of 2,400 bytes a level it takes about 437 chained levels to reach 1 MB, and a Win32 build with its smaller frames would need more than that. A different compiler gives different frames; the method is just the prologue.

## c) Why not allocate it with the number of followers.

**Answer.** Happy to, and I will send it in whatever shape you prefer — it is your call. The short reason I would grow the list instead of sizing it from a count is that `NArray` removes the magic number and the `break` that drops a follower at 64 outright, with no counting pass to add and no cleanup path to get wrong — details under Proposal below. One thing worth knowing first: counting the followers turns up a separate defect, which the sizing change does not fix and which I would rather not bury.

To size the array you must count the followers in a pass of its own, and whenever two followers sit next to each other in `Things` the collecting pass gathers **fewer** than the count. The allocation itself stays safe — the placement loop is bounded by `gwc`, not by the count, so over-allocating harms nothing — but the two passes disagree, and the gap between them is a defect of its own that sizing the array does not touch. My patch took the cheap route instead and added a `break`, which turns an overflow into a silent drop and leaves the magic number where it was. `GoWith[gwc++]` ([Feature.cpp:909](https://github.com/rmtew/incursion-roguelike/blob/7469d3eddf1c4347928854a9494eeefb301d358e/src/Feature.cpp#L909)) is not tested against 64 at all today, which is why I touched the function.

**Measured.** The collecting loop is already losing followers. I instrumented it to record each follower's index in `Things` before it ran, what it gathered, and what was still standing on the old level afterwards, then gave a wizard-mode character kobolds and made each one a follower:

```
seed 3362:
MoveDepth depth=1 followers_before=3 at=[393,394,395] collected=2 left_behind=1
```

Ten seeds, one run directory each; nine reached a level change. Every session whose followers were consecutive in `Things` lost exactly one, silently. The control is seed 777, whose two followers sat at 395 and **397**, with one index between them: both arrived. The log records where the followers were, how many came and how many stayed, but not which one stayed. Table and logs: [docs/evidence/inc-90u](https://github.com/networkingguru/incursion-roguelike/tree/1ef5f2988240ed16a1019bbec8014e46cbc3d284/docs/evidence/inc-90u), reproduction keys in [tools/keys/followers.keys](https://github.com/networkingguru/incursion-roguelike/blob/1ef5f2988240ed16a1019bbec8014e46cbc3d284/tools/keys/followers.keys). Seed 3362 arrives on depth 2 with two kobolds beside the player (`screen-arrived-depth2.txt`); sixty turns later the same session shows one live kobold and one kobold corpse, with a black orc named in the interrupt prompt above them (`screen-after-60-turns.txt`). No third kobold appears in either.

**Read from the source, not run.** The loop walks by index ([Feature.cpp:906-911](https://github.com/rmtew/incursion-roguelike/blob/7469d3eddf1c4347928854a9494eeefb301d358e/src/Feature.cpp#L906-L911)): `MapIterate` advances with `i++` ([Base.h:78-79](https://github.com/rmtew/incursion-roguelike/blob/7469d3eddf1c4347928854a9494eeefb301d358e/inc/Base.h#L78-L79)), `c->Remove(false)` deletes that creature from `m->Things` ([Display.cpp:1130](https://github.com/rmtew/incursion-roguelike/blob/7469d3eddf1c4347928854a9494eeefb301d358e/src/Display.cpp#L1130)), and `Array::Remove` memmoves the tail one place left ([Base.cpp:535](https://github.com/rmtew/incursion-roguelike/blob/7469d3eddf1c4347928854a9494eeefb301d358e/src/Base.cpp#L535)). The entry after a removed one slides into the index just finished with, and `i++` steps over it. Three consecutive followers therefore yield the first and the third; two consecutive yield only the first. Nothing brings the straggler along later either: the turn loop iterates the player's current map only (`Main.cpp:220`), so a creature on another level takes no turns, and a monster that reaches stairs goes through `Thing::MoveDepth`, which deletes it. `Game::LimboCheck` (`Feature.cpp:820`) looks like the mechanism that would bring one back, and it is inert three times over: nothing calls it, no shipped script calls `EnterLimbo` to park anything, and `EnterLimbo` never assigns the `Target` that `LimboCheck`'s first branch tests at `:827` — its second branch would then read an uninitialised `p` at `:842`. Other code moves creatures between maps — `Feature.cpp:270` and `:278` for dungeon entry and return, and several spells — but this loop is the only thing that brings a player's followers with him. What it carries is whatever `ts.isLeader(this)` accepts, which is a creature whose first *valid* leader-type target — leader, summoner, master or mount — is the player (`Target.cpp:903-921`): summoned creatures and animal companions, which get there through `MakeCompanion` adding a `TargetSummoner` (`Social.cpp:2414`). No charmed creature is collected: `Status.cpp:675` routes `CH_DOMINATE`, `CH_ALLY` and `CH_COMMAND` into `MakeCompanion`, and `:677` immediately calls `ts.removeCreatureTarget(oCreature(s.h),TargetAny)` — `s.h` being the player, tested at `:674`, which invalidates every entry naming the player — the one just added included — after which `Retarget` rebuilds without it. A charmed creature can still become a follower later by another route, `Skills.cpp:1172` or `Social.cpp:743`, and then it is collected. Mounts are a separate case and are never collected: `Skills.cpp:4272` removes the mount from `m->Things` and re-attaches it by assigning `m`, `x` and `y`, so `MapIterate` cannot see it at all.

**Proposal, not yet written.** Drop the counting pass and grow the list instead. `NArray` is already the container `Map::Things` uses ([Map.h:184](https://github.com/rmtew/incursion-roguelike/blob/7469d3eddf1c4347928854a9494eeefb301d358e/inc/Map.h#L184)); it grows on `Add` and frees itself in `~Array`, so there is no magic number, no `break` that drops a follower at 64, and no cleanup path to get wrong. I would use `NArray<hObj,5,5>` rather than invent a new size, because `Base.cpp` instantiates the template explicitly and `Array<hObj,5,5>` is already on that list — a fresh `<8,8>` would need a line added there or it will not link. I would store handles rather than `Thing*` as well. Nothing dangles today — `Remove(false)` only unlinks, and the `F_DELETE` flag and the destroy queue are both behind `isDelete` (`Display.cpp:1171-1186`) — so that part is defensive rather than a fix. No STL is involved: the game's own sources use none, and the only `std::` uses in `src/`, `inc/` and `lib/` are two `std::wstring` locals in the platform layer.

One detail I checked before proposing a local: `Array::Array()` returns early while the registry is loading, before it assigns `Items`, so a stack-local `Array` would destruct on an unset pointer if it were ever constructed inside that window. `MoveDepth` is reached only from gameplay and the window is inside `Registry::LoadGroup` (`Registry.cpp:561` to `:705`), so the two cannot overlap.
