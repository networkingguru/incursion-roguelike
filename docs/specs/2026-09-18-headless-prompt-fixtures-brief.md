# check_headless.sh steps 8-10: load a character, stop diving for prompts

Bead: inc-gjzx. Lane: `tools:`. Label: internal.

## Goal

`tools/check_headless.sh` steps 8, 9 and 10 must pass again, and must stay
passing across module changes. They prove that `tools/headless.sh` can tell
three session endings apart:

- step 8: the run is parked at the unanswered death prompt, `Die? [yn]`
- step 9: the run answered that prompt and really died
- step 10: the run is parked at the threat-disengage prompt

## Why they fail now (measured 2026-09-18 at b443f8f)

All three drive `tools/keys/dive.keys` at a pinned seed and wait for the world
to produce the prompt they want. The world no longer does.

| seed | turns | stalls at key | where the session actually ends |
|---|---|---|---|
| 1 | 8,464 | 531 | `Do you want to stop searching (constitution drain…` — a `[yn]` prompt |
| 11 | 315 | 369 | the in-game help browser, combat manual (`mode 5`, MO_HELP) |
| 42 | 1,541 | 219 | `Confirm enter the magma? [yn]` |

Two separate causes sit under that.

**1. `dive.keys` cannot answer any modal prompt.** Its whole alphabet after
character creation is `w p s . " digits "`, ENTER and the arrows. It holds no
`y`, no `n`, no ESC. `TextTerm::yn` (`src/Term.cpp:3338`) loops until it reads
`y` or `n`. So the FIRST `[yn]` prompt the world produces ends that session's
gameplay, whichever prompt it is. Which one comes first is a property of the
generated world, so it moves whenever `lib/` moves. Steps 8 and 9 assume the
death prompt comes first. It does not any more.

**2. The threat prompt is now escapable, and it escapes into the manual.**
`src/Move.cpp:941` asks `ChoicePrompt("You are in a threatened area. Abort,
Flee or Disengage?", "afd?")`. The `?` choice opens the combat manual at the
`{LE}` anchor (`src/Move.cpp:943`, `lib/help.irh:3320`) and then re-asks.
Commit f7ff2d7 (2026-08-28, bead inc-es62) gave every `ChoicePrompt` highlight
navigation: an arrow key moves the highlight, ENTER picks it. `dive.keys` is
full of arrows and ends each depth block with ENTER, so roughly one time in
four it picks `?`, opens the manual, and never leaves — the script has no ESC.
Seed 11 does exactly this. Before f7ff2d7 no key in `dive.keys` could answer
that prompt at all, which is the behaviour step 10 asserts.

So a seed repin cannot fix step 10. A scripted dive that carries arrows and
ENTER can no longer be relied on to PARK at that prompt.

**3. The threat detector can be satisfied by the wrong screen.**
`assert_stuck_at_threat_prompt` and `tools/headless.sh:343` both grep the last
screen for the bare words `threatened area`. The combat manual page that the
prompt itself opens contains those words. So a session that escaped the prompt
into the manual would be reported as frozen AT the prompt. That is a detector
that cannot fail correctly, which `docs/VERIFICATION.md` forbids.

## Approach

Stop generating a world and hoping. Load a frozen character who is already
standing next to a hostile monster, then drive the two prompts deliberately.
This is the direction bead inc-ye7o already names, and the machinery is built:
`INCURSION_LOAD`, `tools/make_char_fixture.sh`, `tools/fixtures/chars/`, all
described in `tools/fixtures/README.md`.

One fixture serves all three steps, because the two prompts need the same
world state and are reached by different first keys:

- step 10 moves AWAY from the monster on the first key. The threat prompt
  fires before any damage, and the game blocks there, so nothing else can
  happen.
- steps 8 and 9 rest in place until the monster kills the character. Resting
  never leaves the threatened square, so the threat prompt cannot fire.

## Phases, one commit each

**Phase 1 — make the threat detector honest.** Change both greps from
`threatened area` to the prompt's own words, `Abort, Flee or Disengage`. Add a
`--selftest` case that feeds the assertion a screen holding the combat manual's
`{LE}` text and requires it to REJECT that screen. Prove the case red against
the old grep before you change it, and say so in the report. Steps 8-10 stay
red until phase 4; that is expected.

**Phase 2 — build the fixture.** Author `engaged-hostile-save.keys`. Base it on
an existing save-making script (`tools/keys/lizardfolk-monk-save.keys` is the
worked example the README names). `tools/keys/assassin-engaged-target.keys`
holds the exact wizard-summoning idiom to copy:

```
w
@choose "Monster Summoning"
@choose "<group>"
@choose "<monster>"
RIGHT ENTER
@until "HP:" ESC
```

Then make the fixture with `tools/make_char_fixture.sh`. Choose the monster
empirically against these requirements, and RECORD what you chose and why in
the key script's header:

- it must be hostile, awake and able to perceive the player, or `src/Move.cpp`
  will not ask the threat question at all;
- resting beside it must kill the loaded character, at the pinned seed, well
  inside the rest budget of phase 3;
- the square the character steps to in phase 3 must be walkable.

Prefer the weakest monster that meets those. State the number of rest keys the
death actually took.

**Phase 3 — author the three loaded key scripts.** Each ends with a `@dump`
and `@quit`, because every assertion reads the LAST screen file.

- `threat-freeze.keys`: one movement key away from the monster, then `.`
  repeated. After the prompt is up the script MUST NOT send an arrow, ENTER,
  ESC, `a`, `f`, `d` or `?`. `.` is safe: `ChoicePrompt` ignores it.
- `death-freeze.keys`: `.` repeated until the monster kills the character, and
  nothing else. `.` cannot answer `yn()`, so the session parks.
- `death-confirm.keys`: the same, then `y`.

Run each one and confirm the final screen by eye before moving on.

**Phase 4 — rewrite steps 8, 9 and 10.** Keep every existing assertion pair,
including the negative ones (the death scenario must not be read as
threat-frozen, and the reverse). Replace only how the scenario is produced:
`INCURSION_LOAD` naming the fixture, `INCURSION_OPTIONS` still naming
`tools/gates/Options.Dat`, because step 8 needs `OPT_NODEATH` on. Update the
block comments to say what the scenario now is; the current ones describe
`dive.keys` and would become lies.
